# 血源诅咒 PC（bbport）制作笔记

适用：bbport 0.9.33 / eboot 1.09。PS4 模拟器（shadPS4 等）内存布局不同，不通用。

## 一、内存模型

| 项 | 值 |
|---|---|
| 镜像（guest）基址 | `0x800000000` |
| 玩家对象指针槽 | `0x80553B0E0`（静态，跨重启/换图不变） |
| 对象本身 | `[[0x80553B0E0]]`，实测长期稳定在 `0x1008067310` |

对象内部的偏移（int32）：

| 偏移 | 含义 | 备注 |
|---|---|---|
| `+0x154` | 血量显示值 | 每帧由游戏从真实血量算出 `min(当前,上限)`，**写它无效** |
| `+0x158` | 血量上限 | 与 `+0x154` 成对出现，容易被误判为"当前/上限"对 |
| `+0x160/+0x164` | 体力显示值 / 真实体力 | 结构同上 |
| `+0x180` | 活力，之后步长 8：耐力/力量/技巧/血质/秘法 | 每项 4 字节、隔 4 字节填充 |
| `+0x1C4` | 洞察 | 上限 9999 |
| `+0x1D0` | 等级 | 独立字段，**不是**由属性算出来的 |
| `+0x1D4` | 血之回响 | 上限 999,999,999 |
| `+0x8B8` | 水银弹数量 | |
| `+0x8E8` | 血瓶数量 | |

## 二、难点：血量主值

现象：`+0x154` 写进去会被立刻改回，因为它是显示值。

真实血量在**另一个分配块**里，结构为 `{handle, 16, 当前血量, 上限}`，
通过 `[[context+0x3B0]+0x20]+0xF0` 到达（`context` 每次换图都会变，无法当锚点）。

定位流程（可复用）：

1. 让血量不满，用「(当前, 上限) 相邻 int32」做 **qword 精确扫描**（一次扫到，命中极少）；
2. 候选逐个写入上限，**看玩家对象里的显示值是否跟着变** —— 跟得动的才是上游；
3. 注意 **满血时这个判据失效**（写满值等于没写，全部"假成功"），必须改用 `上限-7` 当探针，
   且要求"写进去的值本身没被立刻改回"；
4. 扫描范围不能想当然：真实血量与玩家对象**同一个分配块**（约 200MB~2GB 范围内浮动），
   而不是那片 10GB 的公共堆 —— 后者只有镜像副本。

## 三、扫描范围踩坑（重要）

一开始把范围写死成 `0x010006000000 ~ 0x010282000000`（10GB 池），结果永远只找到副本，
写入无效、`锁血` 静默失效。用断点从显示值的写入指令里取到 `RAX`，再反推 `RAX+0xF8`，
一查 `VirtualQuery` 才发现真实血量在**另一个分配块**，且离玩家对象只有约 210MB。

结论：**不要假设堆布局**，先 `VirtualQuery` 看分配块；定位优先在"已知稳定对象"附近扫。

## 四、代码补丁尝试（失败，留档避免重复踩）

每帧刷新血量的函数（`0x801A0D7D0` 附近）：

```asm
801A0D7B1  mov  ecx,[rax+0xF8]     ; 上限（来自 ChrIns 参数结构）
801A0D7C1  mov  edx,[r12+0x18]     ; 真实血量
801A0D7C4  cmp  edx,ecx
801A0D7C6  cmovg edx,ecx
801A0D7C9  mov  [r12+0x14],edx     ; 写显示值
```

- 该函数**所有角色共用**（`rdi` 传对象），无条件改成"写满值"= 主角和敌人一起无敌；
- 想只对主角生效必须做条件补丁，判据要么是对象指针（每次换图变），要么是 tag（未验证唯一）；
- 另：注入时 `jmp 远处标签` 在 CE 里会生成 **14 字节绝对跳转**，会踩坏后续指令，
  必须手写 `db E9 / dd 目标-地址-5` 并完整重放被踩指令 —— 否则直接崩游戏。

## 五、其它经验

- 属性写入会持久（活力 10→11 保持），但**等级要一起改**，否则等级与属性不自洽；
- 改完属性要重新打开状态面板，界面才刷新；
- 血瓶/水银弹数量会写进存档，关掉不回退；
- 读取界面数值做校验：全屏游戏用 `PrintWindow(hwnd, hdc, 2)` 抓帧，比屏幕截图可靠（不受遮挡影响）。

## 六、体力（无限体力实现）

体力与血量在同一块 ChrIns 参数结构里，**相对血量主值偏移 +0x30**：

| 相对血量主值 | 含义 |
|---|---|
| `+0x30` | 体力当前值（写入生效，实测 131→30 后界面同步） |
| `+0x34` | 体力上限（当前值下降时保持 131 不变） |

对象侧的 `+0x160 / +0x164 / +0x168` 是显示值与副本，写它们无效。

实现：锁定 `[血量候选 + 0x30] = [血量候选 + 0x34]`，120ms 一次即可（不需要扫描新地址，
因为血量候选已经定位好了，体力就在同一结构里）。

## 七、体力（v1.6.2 更正：上面第六节的字段判断有误，以此节为准）

> 第六节记录的 `+0x30 / +0x34`（131 组）经 20+ 次真实按键复测，**不是攻击消耗池**——真实攻击期间变化次数为 0，属另一条无关 gauge。以本节为准，第六节保留作历史记录。

### 真实体力池
| 字段 | 含义 | 实测 |
|---|---|---|
| `driver+0x3C` | 体力当前 | 每次真实攻击按招式扣一档（16 或 30/击，随武器/招式） |
| `driver+0x40` | 体力上限 | 恒 110 |
| `obj+0x170` / `obj+0x174` | 显示 / 上限镜像 | 晚 driver 14~17ms 跟随 |
回复：最后一次消耗后 400~500ms 起，约 30~60/s，封顶 110。

### 实现
- 唯一写点：`driver+0x3C := driver+0x40`（每 tick 现读上限、写前二次比对、只在 cur<max 写、带 pcall）。
- 频率 **12ms**（60ms 会留下约 60ms 可见下陷；12ms 时正常消耗最多造成 ≤1 帧显示抖动，属正常）。
- 定位（只读、零探针）：每 tick 重解析静态槽 `0x80553B0E0`；用 hp 对 `(obj+0x154,obj+0x158)` 的 8 字节精确 qword 有界扫描（旧驱动 ±32MB → obj ±512MB → ±2GB，预算 1.5s，**禁止全地址空间**）；命中后用四字段交叉校验 `+0x00/+0x04/+0x3C/+0x40` 与 obj 镜像比对；候选基址 `%8==0` 硬过滤；PASS=1 才绑定。
- 换图自愈：驱动字段不自洽 2 tick（24ms）即丢弃并立即重定位；死块检测用「镜像持续低迷 ≥6 tick 且 ≥150ms」判死（计数与是否写入解耦，否则"死块自称已满"的形态永远判不出来）。

### 已知限制
- 判死 + 重定位期间最坏约 **1s 零写入**（换图时通常表现为立即）。
- 极少数「换图后旧驱动块被释放但内容看似正常」的情形：**取消勾选 `[23]` 再重新勾选一次**即可恢复。
- 玩家闲置（体力始终满）时无法判定死块，窗口内最多误写 1 次。
- 翻滚/冲刺键位在本移植版未验证到掉体力，验收以左键/RMB 为准。

### 验收方法（必须真实输入，禁止自证）
1. 不勾选对照：真实左键 5 次，必须看到每击一档固定下降。
2. 勾选后同样按键：`obj+0x170` 零下陷（允许 ≤1 帧）；RMB 重击同样零下陷；静止 30s 零下陷。
3. 取消勾选后消耗恢复；4. 换图后重复第 2 步。
**禁止**用 `writeInteger` 冒充"消耗"——写入点与验证点重合就是循环论证（v1.6.1 就是这样"验证通过"却实际无效的）。
